# Importing primary TXT into COJ

The primary authoring data lives in two separate Git repositories. This importer
copies committed TXT into COJ and generates its computational XML using the
existing COJ converters. It is **one-way and manually invoked**: no background
checks, automatic pulls, source writes, commits, or pushes.

## Source mappings

Paths below are relative to `D:\Lanxin\Desktop\ONCOJ` by default.

| Committed source | COJ TXT destination | Generated XML |
|---|---|---|
| `oncoj_source/trees/*.txt` | `data/txt/trees/` | `data/xml/trees/` |
| `senmyo_norito_project/EN_SM_trees_table/*.txt` | `data/txt/text/` | `data/xml/text/` |
| `oncoj_source/saywopimye.txt` | `data/txt/dict/dictionary.txt` | `data/xml/dict/dictionary.xml` |

Only regular, committed files at these locations are imported. Corpus folders
are not scanned recursively. Each repository's local HEAD commit is recorded;
uncommitted source changes and source Git line-ending transformations are not
imported. TXT is copied exactly from the committed Git blob, not normalized.

## Normal update workflow (PowerShell)

First finish or safely preserve your work in the primary repositories. Pull
their updates yourself when appropriate:

```powershell
git -C D:\Lanxin\Desktop\ONCOJ\oncoj_source pull
git -C D:\Lanxin\Desktop\ONCOJ\senmyo_norito_project pull
```

Then run the preview from COJ:

```powershell
cd D:\Lanxin\Desktop\COJ
python scripts/data_conversion/import_primary_txt.py --preview --normalize-xml
```

Read `.primary-txt-import/preview.txt`. It lists both source commits, source
changes, files that would be replaced, warnings, and blockers. The detailed
machine-readable plan is `.primary-txt-import/preview.json`.

With `--normalize-xml`, this is a two-step preview: genuine TXT/XML content
updates first, then canonical formatting of the entire post-import corpus
under `data/xml/`. XML changes that are formatting-only are deferred to step 2.
The preview explicitly reports each step. `--apply` executes both saved steps
in that order and updates the manifest with the final canonical fingerprints.
Do not add `--normalize-xml` to apply: apply follows the approved saved plan.

Without `--normalize-xml`, the importer retains its narrower line-ending-only
exception and does not perform full-corpus normalization. For the canonical
corpus workflow, use the two-step command shown above.

**Preview does not replace corpus/dictionary TXT, XML, or the import manifest.**
It stages proposed replacement bytes under the ignored `.primary-txt-import/`
directory. A new preview supersedes the previous plan. If a new preview fails,
the previous plan cannot be applied accidentally.

After reviewing a successful preview, explicitly apply it:

```powershell
python scripts/data_conversion/import_primary_txt.py --apply
```

Stop editing corpus/dictionary files and stop any application that could save
them while applying. The importer locks out other importer runs, but this lock
cannot prevent independent editors or applications from writing those files.

Apply rechecks the source HEAD commits, conversion fingerprint, local file
fingerprints, Git status, and staged payloads. If any relevant state changed,
it stops: resolve the situation and produce another preview. Source commits
are immutable snapshots; apply never substitutes newly fetched data.

Review `git diff` and commit the data and `data/primary-txt-import.json` together
after a successful apply. Do this before the next import; uncommitted managed
data is deliberately a blocker. Restart browsing applications after updating
to clear any cached old data. The importer does not restart applications.

On another computer, specify the directory containing the two repositories:

```powershell
python scripts/data_conversion/import_primary_txt.py --preview --normalize-xml --source-root /path/to/ONCOJ
```

Apply uses the repository paths recorded by that preview, so no source-root
argument is needed for apply.

## Incremental behavior

The persistent import manifest records both source commits, source and COJ
file SHA-256 fingerprints, validation counts, and conversion-code fingerprint.
A fingerprint is a value calculated from the bytes of a file; dates alone are
not used to decide whether it changed.

- First import: convert all mapped files to establish the baseline. `added`
  means new to the import record, not necessarily absent from COJ.
- Later imports: regenerate only files whose source bytes changed, plus newly
  added files. One corpus change normally replaces one TXT/XML pair.
- Dictionary change: regenerate the complete dictionary XML, not individual
  entries. It is currently stored as one document.
- Same generated bytes: leave that file untouched, including its timestamp.
- XML that differs **only in line endings** is retained, including its bytes
  and timestamp. The importer maps CRLF and lone CR to LF for this comparison
  and checks byte equality; it does not ignore spaces, indentation, attribute
  order, a byte-order mark, or any other difference. TXT still uses exact bytes.
  The preview lists each retained XML. The manifest records the retained file's
  actual fingerprint, the generated XML fingerprint, and their normalized
  fingerprint, so later imports do not mistake retained line endings for a
  local edit. Local-edit safeguards still apply before this exception.
- New source commits with no mapped content changes: update provenance only.
- Identical source commits, converter and output state: apply is a no-op.
- Conversion-code fingerprint change: preview a full XML regeneration. This
  conservatively fingerprints all Python files under `src/coj`, `txt2xml.py`,
  the importer, and the Python major/minor version; some unrelated package
  changes may therefore also trigger regeneration.

The manifest identifies the current imported state, not a complete review or
revision system. Committing manifests to Git preserves successive import
records. The source repositories remain the authoring authority.

## Canonical XML formatting

The shared formatter is `src/coj/xml_format.py`. Corpus/dictionary string and
file serializers use it, including `CorpusDocument.to_file()`; generated XML
therefore follows the same conventions as the normalization step.

- Attributes sort alphabetically by their exact qualified names (case-sensitive).
- Element-only layout uses two-space indentation.
- Empty elements use `<tag />`, with attributes sorted if present.
- Whole documents use `<?xml version="1.0" encoding="utf-8"?>`, UTF-8 without
  a byte-order mark, LF line endings, and one final newline. Entry/block fragments
  omit the declaration.
- `.gitattributes` pins `data/xml/**/*.xml` to LF on Git checkout, so Windows
  `core.autocrlf` cannot undo this canonical line-ending convention. It does
  not apply to historical run/workspace XML.
- Child elements are never sorted or moved. Attribute values and leaf text,
  including leading/trailing spaces, stay unchanged as parsed XML.
- Mixed content, inline word-separating whitespace, and `xml:space="preserve"`
  are retained rather than subjected to pretty-print indentation. Literal CR
  characters in text/attributes are escaped where needed to preserve meaning.
- Comments, processing instructions and namespace prefixes are retained.

Each normalization checks the parsed content/order before and after formatting.
CDATA sections retain their character content and section boundaries. This is
presentation normalization, not exact source-byte preservation. Unsupported
DTDs and malformed XML block the workflow instead of being discarded.
This is the project's readable canonical format, not the W3C XML C14N protocol.

Normalization is explicit and reproducible: rerun the two-step preview command.
It examines **only `data/xml/**/*.xml`** (currently 116 files), including files
unchanged by the import. Historical XML in `scripteditor/runs/` and workspace
copies in `compreditor/workspace/` are excluded and remain untouched. An
already-canonical file is not replaced.

## Overwrite and deletion safeguards

Uncommitted changes to managed COJ files block apply, including new untracked
files. Unrelated source-code/documentation changes do not block it.

After the first import, even a **committed** local corpus change is detected by
comparison with the previous import fingerprints. It is not silently replaced.
Missing previously imported TXT/XML is also a local change.

Source deletions, renames, and extra COJ corpus TXT/XML files absent from the
source mapping are reported as blockers. This version provides **no deletion
override**: an explicit decision and a separately agreed resolution are needed.
Do not delete or alter the manifest merely to bypass a conflict.

Before the first import, there is no historical import baseline. Git status
protects uncommitted files, but cannot identify committed COJ-only changes as
local edits. The first full preview is the opportunity to review replacement
of that existing committed data.

## Validation and its limits

Regenerated files are checked for UTF-8 input, a nonempty parsed model,
well-formed XML, expected XML root, and the same model-unit count after XML
reloading. Duplicate dictionary IDs and entry-heading/count mismatches are
reported as warnings rather than silently presented as losslessness guarantees.

These checks **do not prove linguistic correctness, structural equivalence of
every source annotation, or complete semantic losslessness**. Conversion uses
the current parser/serializers without changing their historical behavior. See
[round-trip limitations](txt-xml-roundtrip.md) and [data issues](data-issues.md).
Existing dictionary field limitations and unusual corpus annotations remain
possible; review warnings and the first generated outputs before applying.

## Apply failure and local storage

Apply backs up files it will replace, then replaces each file individually and
writes the provenance manifest last. Ordinary detected failures attempt to
restore the originals. Individual replacements are atomic, but the entire set
of TXT/XML files is **not** a single filesystem transaction; readers must not
browse an update in progress.

An interrupted process or failed rollback leaves a transaction record at
`.primary-txt-import/transaction.json`. Further imports stop for inspection.
The record identifies target files and backups; a null backup means the target
did not exist before apply. There is no automatic crash-recovery command.
Inspect/recover with assistance rather than blindly retrying. A stale
`import.lock` likewise requires checking that no importer is still running.

The ignored local directory retains staged replacement payloads, preview
reports, and apply backups. Only proposed replacement files are staged, and
only files being replaced are backed up—not full source repositories. Old
preview payloads and backups are not automatically deleted. They consume local
storage but are not uploaded by ordinary Git commits. Keep them while reviewing
or recovering an import; cleanup/retention is not implemented by this tool.

Exit status `0` means success; `2` means a blocked or failed import. The report
describes the reason. Nothing writes back to either primary repository.
